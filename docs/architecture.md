## Стек

- Backend: Go, `net/http`, PostgreSQL, pgx, goose.
- Фоновые задачи: worker для импорта и публикации outbox.
- Push-уведомления: отдельный Go-сервис `notifications`, Kafka через franz-go, Web Push.
- Frontend: React, TypeScript, Vite, CSS, `fetch`.
- Локальный запуск: Docker Compose; nginx раздаёт frontend и проксирует `/api/`.

Проект состоит из одного Go-модуля и трёх отдельных процессов: API, worker и `notifications`.

API обрабатывает пользовательские запросы, worker импортирует операции и публикует события в Kafka, а `notifications` независимо отправляет push-уведомления.

Основные модули backend: пользователи, бюджет, операции, правила, цели и уведомления. Источник банковских операций на первом этапе — локальный mock API.

## Данные и события

PostgreSQL хранит пользователей, категории, бюджеты, операции, правила, цели, взносы, уведомления и аудит. Пользователь имеет доступ только к своим данным.

Операция уникальна по `(bank_connection_id, external_id)`. Повторный импорт неизменённой операции безопасно пропускается. Если источник прислал другие данные с тем же ID, импорт завершается ошибкой конфликта.

Финансовые изменения пользователя за месяц сериализуются через `ledger_periods`. Изменение операции, аудит, проверка лимитов и создание события выполняются в одной транзакции.

Дашборд читает актуальные данные напрямую из PostgreSQL.

Kafka используется только для асинхронной доставки push. Сначала событие сохраняется в DB outbox, затем worker публикует его в Kafka и помечает отправленным только после подтверждения брокера.

`notifications` сохраняет полученное событие и задачу доставки до подтверждения Kafka offset. Повторная доставка события не создаёт вторую задачу. Временные ошибки отправки push повторяются. На клиенте ID уведомления используется для защиты от повторного показа.

Сбой Kafka или push не влияет на сохранность финансовых данных и работу центра уведомлений.

`notifications` владеет своими push-подписками, inbox и задачами доставки. Они находятся в отдельной схеме PostgreSQL с отдельными миграциями и DB-пользователем. На первом этапе PostgreSQL общий, но сервис не читает таблицы основного backend.

API регистрирует и удаляет push-подписки через внутренний API `notifications` после проверки пользователя. Внутренние запросы аутентифицируются.

Событие содержит всё необходимое для отправки push: ID уведомления, ID пользователя и данные сообщения. Обращаться к финансовым таблицам сервису `notifications` не требуется.

REST API размещается под `/api/v1`, контракт хранится в `api/openapi.yaml`. Событие первого этапа — `budget.threshold_reached.v1`. Маршрут `/api/health` остаётся без изменений.
