# Smart Budget

## Запуск

Нужны запущенный Docker и Make. `make up` создаст недостающие секреты и VAPID-ключи в `.env`, применит миграции и запустит сервисы.

```sh
make up
```

Приложение: http://localhost:3000. Порт frontend задаётся через `FRONTEND_PORT` в `.env`; при его смене обновите `APP_ORIGINS`. Backend доступен внутри Docker-сети, запросы `/api/` проходят через nginx.

| Команда | Действие |
| --- | --- |
| `make down` | Остановить контейнеры, сохранить данные |
| `make logs` | Смотреть логи |
| `make lint` | Проверить Go, TypeScript и форматирование |
| `make lint-fix` | Исправить форматирование |
| `make test` | Go-тесты с Kafka/PostgreSQL и frontend-тесты HTTP/refresh/push |
| `make generate` | Пересобрать Go-методы из SQL через sqlc |
| `make check-generated` | Проверить актуальность сгенерированного кода |
| `make migrate` | Применить SQL-миграции |
| `make migrate-status` | Показать состояние миграций |

В GoLand открывайте корень проекта: `go.work` подключает модуль `backend/`. В Settings → Go → Go Modules должна быть включена `Enable Go modules integration`. В Go SDK выберите Go 1.27.1 или новее, как требует `backend/go.mod`.

## PostgreSQL

База `smart_budget` запускается в Docker (`postgres:5432`), данные сохраняются в volume. API, worker и notifications используют отдельные DB-роли. Миграции — `make migrate`. Начальная схема — `backend/migrations/001_init.sql`, таблицы notifications — `backend/migrations/notifications/001_init.sql`. У каждого потока своя история goose.

На локальном этапе старые миграции объединены: для базы с прежней историей нужен сброс данных. Дальнейшие изменения добавляйте отдельными файлами `002_*.sql`, не переписывая применённые миграции.

SQL-запросы — в `backend/queries/{api,outbox,notifications}`, сгенерированный код — в `backend/internal/db/`. После изменения запросов или миграций выполните `make generate` и добавьте результат в коммит. Конфигурация — `backend/sqlc.yaml`; goose остаётся мигратором.

## Kafka

Kafka доступен по `kafka:9092`. Worker публикует outbox в `notifications.requested.v1`, notifications читает события.

## Авторизация

На странице доступны регистрация по email и паролю, вход и выход. Пароль — от 8 символов до 72 байт UTF-8. Часовой пояс при регистрации берётся из браузера; API использует UTC, если он не передан.

API: `POST /api/v1/auth/register`, `/auth/login`, `/auth/refresh`, `/auth/logout`, `GET /api/v1/auth/me`. Изменяющие запросы требуют разрешённый `Origin` и `X-CSRF-Protection: 1`. Регистрация и вход ограничены суммарно 10 попытками на email за 15 минут.

JWT хранится в HttpOnly-cookie на 15 минут. Refresh-токен ротируется при обновлении; абсолютный срок сессии — 30 дней. Frontend обновляет access автоматически. Выход отзывает текущую сессию, другие устройства остаются авторизованы. `make init` создаёт `JWT_SECRET`; для HTTPS задайте `AUTH_COOKIE_SECURE=true` и соответствующий `APP_ORIGINS`.

Поддержки анонимных аккаунтов нет: регистрация всегда создаёт нового пользователя с обязательными email и хешем пароля. Подтверждение email и восстановление пароля пока не реализованы.

## Notifications

После входа доступны макет бюджета и панель уведомлений. Данные бюджета пока демонстрационные.

На странице нажмите «Включить push», разрешите уведомления, затем «Отправить тест». Сначала зарегистрируйтесь или войдите: подписка и история привязаны к пользователю. Подписка привязана к серверной сессии: закрытая вкладка не мешает доставке, истечение сессии или выход прекращают новые отправки. Frontend дополнительно удаляет подписку браузера; ошибки этой очистки не отменяют серверный отзыв. Между вкладками синхронизируются аккаунт и состояние push.

Notifications хранит подписки в PostgreSQL, проверяет сессию через внутренний API перед отправкой и доставляет Web Push четырьмя параллельными отправителями с повторами до 24 часов. При недоступности API отправка откладывается. Баннер содержит нейтральный текст; подробности доступны в истории. Уже принятое провайдером сообщение может прийти после выхода. Нужен HTTPS или localhost; поддержаны сервисы Chrome, Firefox и Safari. Для своего домена задайте `APP_ORIGINS` и контакт `VAPID_SUBJECT`. Не меняйте VAPID-ключи без повторной подписки браузеров.

## Надёжность и диагностика

Для существующего volume PostgreSQL 17 укажите в `.env` `POSTGRES_IMAGE=postgres:17.6-alpine` и `POSTGRES_VOLUME_TARGET=/var/lib/postgresql/data`. По умолчанию новые установки используют PostgreSQL 18. Переход с 17 на 18 требует отдельного переноса базы; смены образа недостаточно.

Новые миграции `002_*` применяются через `make migrate`/`make up` без сброса volume. Существующие подписки перепривязываются к сессии при следующем открытии страницы; до этого они не отправляют push.

`/api/health` проверяет, что процесс отвечает, `/api/ready` — доступность PostgreSQL (у worker также Kafka). `make logs` показывает причины повторов/отказов, количество ожидающих задач и событий в карантине. Ошибочный outbox не блокирует последующие события; карантин сохраняется для разбора.

Очистка выполняется раз в минуту небольшими пачками: истёкшие/отозванные сессии после 7 дней, счётчики входа после суток, опубликованный outbox и служебные данные notifications после 30 дней. История уведомлений и ключи идемпотентности не удаляются. Replay событий старше 24 часов не создаёт push.

Интеграционные тесты создают отдельные временные базы PostgreSQL и временный Kafka-топик и удаляют их после проверки. Они не очищают базу приложения. Frontend-тесты проверяют координацию refresh и частичную отписку. Реальный показ баннера зависит от браузера и провайдера.
